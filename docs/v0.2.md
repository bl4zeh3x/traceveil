# v0.2 workflow acceptance and demonstration

## 1. Safe batch sanitization

User problem: exporting a group of captures is repetitive, and colliding names or one malformed file should not destroy successful work.

Acceptance: multiple inputs; new, private output directory; no source overwrite; same-name inputs cannot collide; failure isolation; completed manifest with output hashes and counts; no input filenames, original values or raw errors in output. Inputs keep the existing 50 MiB limit; a batch is bounded to 1,000 inputs. Batch artifacts use the original sanitizer unchanged.

Implementation: shared bounded/exclusive file helpers, a sequential batch function, and CLI dispatch. Existing command signatures and sanitizer behavior remain compatible. Tests cover collisions, invalid/missing files, output failure, symlinks, permissions, source preservation, hashes and CLI exit codes.

## 2. Guided privacy review

User problem: knowing that headers were removed does not tell a sender whether retained metrics are safe for a particular recipient.

Acceptance: category counts and actionable next step, residual timing/size/timeline/activity checklist, no original secrets, unknown metadata never copied, empty/malformed capture handling, no claim of anonymity. Raw captures get `sanitize_first`; canonical captures still require `manual_review`.

Implementation: combines the existing inventory with a new residual-risk analysis of sanitized data. This is additional decision support, not a renamed inspect command or a comprehensive secret detector.

## 3. Privacy-safe comparison

User problem: manually comparing individual network reports is slow, and matching capture-local pseudonyms can create false endpoint associations.

Acceptance: reject noncanonical captures on either side; compare request counts, median/p95 durations, known response bytes, unknown sizes, errors and method/status distributions; handle empty captures and zero baselines; do not emit or align endpoint identities; do not modify inputs.

Implementation: allowlisted aggregation, followed by numeric deltas. Tests include exact arithmetic, 200 randomized capture pairs, endpoint independence, malformed inputs, zero denominators, missing sizes and output overwrite refusal.

## Demonstration

Run `python examples/demo_v02.py demo-output` after installing the candidate. Open the generated JSON files in an editor.

1. `batch/manifest.json`: two successful captures and one isolated failure. The manifest uses IDs 1–3, never original names.
2. `privacy-review.json`: canonical capture, `manual_review`, and residual risk guidance. There is no green "safe to share" verdict.
3. `comparison.json`: two requests before and three after, with changed duration and status aggregates. No host or route labels are included.

The `batch/capture-*.har` exports can also be opened with the existing HTML report command. The synthetic input is generated in a temporary directory and removed when the demonstration ends.

## Limitations

Synthetic validation does not establish safety for every real-world capture. Aggregate metrics and relative relationships can still identify an activity. Batch output is not an all-or-nothing transaction: successful files remain after another input fails. A completed manifest identifies the final outcome; interruption or manifest write failure requires inspection and a new destination. There is no upload, replay, secret recovery, telemetry or external asset dependency.
